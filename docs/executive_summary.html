Submitting to the GEMS Prize — step by step

Five steps. The whole thing takes about a minute once the file is on disk.

1 · Get the file

⬇ gemsdoe9-PLACEHOLDER-2314b599.tif

Or press Build in this browser on the overview, which produces the identical pixel field with a fresh name and a fresh hash. Nothing is uploaded from your browser — the GeoTIFF is assembled locally with geotiff_writer.js.

2 · Make the name unique

The DrivenData form does not require a unique file name, but a submission history where every row is submission.tif is useless to you in a week. Use gemsdoe9-<what>-<sha8>.tif. The shipped file already follows this rule; the hash is the first 8 hex characters of its SHA256, so the name identifies the exact bytes.

If you upload the same bytes twice, rename the second one (…-r2.tif) so you can tell the two rows apart.

3 · Open the submission form

drivendata.org → this competition → Submissions → New submission

The dialog says: “You can submit a single-band GeoTIFF (.tif) file, or a .zip file containing a single GeoTIFF, with your predictions. It must match the submission format's CRS, shape, and geotransform.”

Drag the .tif in. (A .zip is accepted too — the browser build can emit one. The competition form also accepts a .zip of a single GeoTIFF, but a .tif is simpler and there is no reason to risk it.)

4 · Write the Note

The Note (optional) box exists so you can tell your own submissions apart later. The example in the form is “clustering with k=25”. For this submission:

GEMSDOE9 FORMAT-CHECK placeholder (no model, no GeoDAWN data) | band-pattern 2.8% | 2314b599

Put the SHA8 in it. Two weeks from now that is the only thing that will tell you which file scored what.

5 · Submit, then check the leaderboard

Submissions are scored on a rolling 7-day window, three per window. Your best public score is what the leaderboard shows. The Initial Prize Round uses a private test set fixed before the competition; the Final Prize Round re-scores your chosen submission against an expanded label set that experts build partly from the Phase 1 submissions themselves.

Rejection: “Predicted values must be in range [0, 1]”

Reported by the team, 2026-09-27

What actually happened The file downloaded from this site was a 49 MB GeoTIFF whose strip-offset table was truncated, so GDAL could not decode it. The platform reported an unreadable file using its value-range error. There was no NaN in it to find.

What is now guaranteed, and how to re-check it yourself:

CheckMeaning
GDAL-READABLErasterio decodes every strip; the file is readable at all
PLATFORM-RANGE0 NaN, 0 Inf, min ≥ 0, max ≤ 1 across all 12,279,160 values
no-nodata-tagno nodata declaration, so no reader can substitute a value
shape / crs / transform / dtype3,292 × 3,730, EPSG:32611, 100 m, float32, 1 band
not-a-known-duplicateSHA256 is not one that already spent a slot
python scripts/validate_submission.py docs/downloads/gemsdoe9-PLACEHOLDER-2314b599.tif

Every line must read PASS. If GDAL-READABLE fails, the file is truncated in transfer — download it again and compare the SHA256.

The exact format, quoted

Problem description, § Submission format — source

  • projected coordinate system for UTM zone 11N, EPSG 32611
  • same resolution as the training data (100m)
  • same bounds as the training data, and data outside the bounds is null or nan
  • single layer with datatype of 32-bit float (float32) with values between 0 and 1 indicating the confidence or probability of fault presence, with higher values indicating higher probability
Why we write 0.0 instead of NaN outside the bounds The spec permits “null or nan” outside the bounds, but NaN is not a member of [0, 1] and a range validator will reject it. 0.0 means “no fault predicted”, which is what a null cell means to the scorer, and it cannot fail a range check. We therefore publish only the all-finite variant and set no nodata tag. Why this was the right call →
