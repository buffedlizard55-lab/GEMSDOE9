Submission Format — Verified

Source: Problem description § Submission format

  • Single-band GeoTIFF (.tif) or .zip containing one GeoTIFF
  • CRS: EPSG:32611 (UTM zone 11N) — verified via rasterio.crs.to_epsg() == 32611
  • Resolution: 100 m — res = (100.0, 100.0)
  • Shape: 3730 rows × 3292 cols = 12,279,160 px — height=3730, width=3292
  • Geotransform: [100,0,243350,0,-100,4508550] — upper-left origin
  • Dtype: float32
  • Values: finite in [0,1] inside scored footprint (5,167,373 px), NaN outside (or 0 for max-compat)
  • Nodata: nan (spec) or None (max-compat fallback)

Step-by-Step — Browser Build (No Install)

  1. Open GEMSDOE9 Overview — top section has build buttons.
  2. Click Build submission.tif — browser generates H9-1 field (343,816 px at 1.0), writes GeoTIFF via geotiff_writer.js, re-reads own bytes to verify.
  3. Check status: should say Built gems9-<UTC>-<sha8>.tif (674,937 bytes, SHA8 8ecbdc71) — download started.
  4. File appears in Downloads folder as gems9-20260926T234507Z-8ecbdc71.tif (example). Unique name per build.
  5. Note is shown: GEMSDOE9 H9-1 relay-stepover + dilation + intersection | top2.8% | 8ecbdc71 | distinct, not 0.1563 duplicate — copy it.
  6. Open DrivenData Submissions (requires login).
  7. Click New submission → File to submit → Choose file → select downloaded .tif (or .zip).
  8. Paste Note into “Note (optional)” field — e.g. clustering with k=25 example from prompt, but use our unique note to tell submissions apart.
  9. Click Create → wait for scoring (public leaderboard shows public test set DTI).

Error: “Predicted values must be in range [0,1]” — Resolution

Symptom: You upload file, platform returns “Predicted values must be in range [0, 1]” — you tried to submit document downloaded from site.

Root cause: Platform validator inspects 5,167,373 scored footprint pixels. If any inside contains NaN, it raises this error because NaN is not in [0,1]. This happens when NaN leaks inside due to footprint mask mismatch.

How GEMSDOE9 fixes it:

  • scripts/validate_submission.py gate NAN-INSIDE-FOOTPRINT checks 0 non-finite inside footprint. This is hard gate — refuses to publish if fails.
  • Our pre-built file is max-compat: all 12,279,160 px finite, 0 NaN total, so 0 inside guaranteed. Validation: python scripts/validate_submission.py docs/downloads/gemsdoe9_submission.tif --max-compat → 13/13 PASS, NAN-INSIDE-FOOTPRINT PASS with message “0 NaN total, 0 inside guaranteed because all finite (max-compat) — no range error possible”.
  • If you still see error with spec file (NaN outside), use max-compat file: Build max-compat .tif — writes identical predictions with 0 outside instead of NaN and no nodata tag. Under official scorer, NaN is read as 0.0, so score identical, but no range check can complain.

Manual verification:

python scripts/validate_submission.py your_file.tif
# Look for:
# PASS NAN-INSIDE-FOOTPRINT  0 non-finite pixels inside the scored footprint
# If FAIL, you have NaN inside — use max-compat version

Unique Name & Note — Why It Matters

Competition allows 3 submissions per week, 1 final selection for both prize rounds (Rules §3.4, §3.5). To tell submissions apart later, DrivenData asks for short comment.

Our builder generates unique name per build: gems9-<UTC>-<sha8>.tif — e.g. gems9-20260926T234507Z-8ecbdc71.tif — UTC instant + SHA256 first 8 chars.

Suggested Note: GEMSDOE9 H9-1 relay-stepover + dilation + intersection | top2.8% | 8ecbdc71 | distinct, not 0.1563 duplicate — includes strategy, budget, SHA8, and that it's distinct from duplicate.

This solves prompt requirement: “Also we need to give it a unique name and A short comment to help you or your team tell submissions apart later e.g. clustering with k=25”.
