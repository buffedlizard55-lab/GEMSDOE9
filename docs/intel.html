STAFF-CONFIRMED 1 · Known catalogue faults are masked from scoring

“Pixels corresponding to known USGS/INGENIOUS faults are masked / excluded from evaluation, so they do not count towards penalty terms.” … “Re-evaluation will also mask/exclude the existing USGS/INGENIOUS faults.”

DrivenData staff (chrisk-dd), 2026-09-16, forum thread 11516 — community.drivendata.org/t/…/11516

Implication (our analysis): predicting catalogue faults is free — it can never add FP penalty, and it can only help where catalogue traces fall within 300 m of withheld new faults. Therefore a safe submission is the union of the catalogue (or a modest dilation of it) plus genuinely new-fault hypotheses. This is exactly why the 0.1563 pattern is a floor, not a ceiling. Our metric implements this masking as fp_ignore_mask (src/gems/metric.py) so holdout evaluation matches the platform.

STAFF-CONFIRMED 2 · Phase 2 label set is built from ALL Phase 1 submissions

“Note that the largest prize pool (Phase 2) will use a test set that is updated by expert review of all Phase 1 submissions, so your fault predictions have an impact on final evaluation even if they are not the most performant in Phase 1.”

DrivenData staff (chrisk-dd), 2026-09-23, forum thread 11527 — community.drivendata.org/t/…/11527. Same structure in the problem description: drivendata.org …/page/967/ (“an expert panel will use submitted predictions to update fault labels for the full region”).

Implication (our analysis): Phase 2 ($250K pool: $100K/$70K/$40K/$25K/$15K per the problem description) rewards well-evidenced contrarian picks: faults we flag that experts verify become part of the final label set. A submission should therefore spend some probability mass on high-evidence fault candidates even where Phase 1 payoff is uncertain — the Phase 2 feedback loop pays for discoveries.

STAFF-CONFIRMED 3 · Test-fault data sources will not be disclosed

“We’re not sharing details about the data sources, fault types, or coverage behind the test faults beyond what’s in the problem description.”

DrivenData staff (chrisk-dd), 2026-09-23, forum thread 11527 — community.drivendata.org/t/…/11527

Implication (our analysis): no shortcut via source-matching. The only way to find the withheld faults is structural/geophysical detection on the provided layers plus permitted external data (rules allow any licensed external data — problem description § External datasets).

STAFF-CONFIRMED 4 · Three scored submissions per rolling week

“The submission allowance resets based on a rolling window, not at a specific date and time.”

DrivenData staff (chrisk-dd), 2026-09-17, forum thread 11524 — community.drivendata.org/t/…/11524

Implication: submission slots are scarce (3 per rolling 7 days). The gate stands: no slot is spent on a candidate that has not beaten the budget-matched random control and the catalogue baseline on our blocked holdout (scripts/lofso_train_eval.py).

VERIFIED 5 · Metric and format (re-checked 2026-09-27 against the problem description)

  • Distance-weighted Tversky index, α=0.2 (FP), β=0.8 (FN), triangular kernel R=300 m (3 px). Source: problem description § Performance metric.
  • Official worked example on that page: TP_w=3.00, FP_w=1.89, FN_w=2.00 → DTI(0.2, 0.8) = 0.60. Our src/gems/metric.py implements these exact formulas; tests/test_validation.py cross-checks the fast and naive implementations to <1e-9.
  • Submission: single-band float32 GeoTIFF, values in [0,1], same CRS (EPSG:32611), resolution (100 m) and bounds as training data; data outside the bounds null or NaN. Source: problem description § Submission format.
  • Reference solution: UNet Monte-Carlo CV, Tversky loss α=0.2/β=0.8, band names read from the GeoTIFF band tags. Source: github.com/drivendataorg/gems-prize-reference-solution (notebook blob sha d45bf7bdb1d3… fetched 2026-09-27 via GitHub API).
